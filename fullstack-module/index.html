The big picture: three programs, one app

15 min
Read

Your web app is really three programs talking to each other. Each one has one job and runs on its own port on your computer:

  • React runs in the browser (port 5173). It draws the page and reacts to clicks. It cannot touch MySQL.
  • Express runs in Node (port 3000). It receives requests, checks them, talks to MySQL, and answers with JSON.
  • MySQL (port 3306) stores the data, as in your Database course.

Why can't React talk to MySQL directly? Because everything in the browser is visible to the user. If React had the database password, anyone could open DevTools, copy it, and delete your tables. The server keeps the password hidden and decides what each request is allowed to do.

A connection pool keeps a few MySQL connections open and lends one to each request. Make it once in db.js and import it wherever you need it.

GET all items, with the category name

The SQL is the same JOIN you wrote in your Database course. pool.execute() returns an array; the first element is the rows, so we destructure it with const [rows].

What MySQL returns (one row)

| id | title          | status | date_reported | category  |
|  1 | Black umbrella | found  | 2026-11-09    | Umbrellas |

What res.json(rows) sends

GET one item, or 404

The ? is a placeholder. The id goes in the array beside the SQL, never glued into the SQL text. Lesson 5 shows why this matters so much.

Done when
  • /api/items shows all 5 items as JSON, with category names
  • /api/items/3 shows the power bank; /api/items/99 shows {"error":"Item not found"}
  • In DevTools → Network, /api/items/99 has status 404
Hint · I get ECONNREFUSED or "Access denied"

ECONNREFUSED means MySQL isn't running: start it in XAMPP. ER_ACCESS_DENIED_ERROR means the user or password in .env is wrong. ER_BAD_DB_ERROR means DB_NAME doesn't match your database. After editing .env, stop the server (Ctrl+C) and run npm run dev again.

LESSON 5 · SESSION 2

SQL injection: why every query uses ?

25 min
Read

SQL injection happens when user input is glued into the SQL text. The database can no longer tell your SQL apart from the user's input, so the user can add SQL of their own. It's one of the oldest and most common attacks on web apps, and it's completely preventable.

Dangerous: string concatenation

Safe: placeholder + values

Try it: what does MySQL actually receive?

Concatenated


            

          

          

            
Placeholder + validation

            

            

          

        

      

    

    

      
Two layers of protection. Placeholders make sure input is only ever treated as a value. Validation (isValidId, validateItem) rejects strange input before it reaches MySQL at all. Use both. mysql2 also refuses to run two statements in one call by default, so tricks like ; DROP TABLE items fail. Don't turn that option on.

Read · state

      
State is data that can change while the page is open: the list of items, whether it's still loading, the search text. You create it with useState. When you call the setter (setItems), React re-renders: it runs your component again and updates only what changed. You never touch the DOM yourself, unlike Week 11.

      
useEffect runs code after the component appears on screen. It's the right place to fetch data. The empty array [] at the end means "run this once, when the page first loads."

Read · the CORS error you will almost certainly see

      
Your page is at localhost:5173 and your API at localhost:3000. A different port counts as a different origin, and browsers block responses from other origins unless the server says "this page is allowed." That permission is a response header, added by the cors package.

    

    

    

      
Why do I see two requests in the Network tab? In development, Vite's <StrictMode> runs each effect twice on purpose, to help you catch bugs. It doesn't happen in the final build, so it's fine.
