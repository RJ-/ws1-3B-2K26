From Database to Web App: Your Initial Design

Your Database final project already has the hard part: tables, keys, and real data. This week you'll plan the web app that sits on top of it. You'll decide which pages it needs, sketch them, pick a look, and build two static pages. In the next weeks you'll connect those pages to MySQL with PHP and JavaScript.

What you'll make

A design package for your final web app, built from your Database project:

  • a one-page project brief (what the app does and for whom)
  • a CRUD map that links every table to the pages that use it
  • a sitemap and one user flow
  • wireframes of at least four screens
  • a small style guide (colors, fonts, buttons, form fields)
  • two static pages in HTML and CSS, filled with your real sample data

Everything goes into one GitHub repository that you'll keep building until the final project is done.

Where this fits

Week 14 · nowPlan and design. Static pages only.
Week 15CRUD with PHP + MySQL. JavaScript form checks.
Week 16Test, debug, and find security holes.
Week 17Finish the full-stack app.

A good plan this week saves you hours later. Every page you sketch now becomes a PHP file in Week 15, and every form field becomes a column in an INSERT or UPDATE.

Rules for this assignment

  • Use your own Database project. If you did it as a group, keep the same group. One member submits the repository link; every member submits their own reflection.
  • No Database project, or fewer than 3 tables? Message me in Classroom before you start. I'll approve a small schema for you.
  • You may change your schema. Designing pages often shows a missing column or table. Change it, and write down what you changed and why (Task 2).
  • No PHP or database connection yet. This week is design and static HTML/CSS only.
  • AI tools: if you use an AI assistant, say in your reflection what you asked it and what you changed. Don't submit designs or code you can't explain.
  • Ask early. Post questions in the Classroom stream with a screenshot.
SETUP

Gather your Database project and make the repository

20 min
  • 1Find these from your Database project: the ERD, the CREATE TABLE script, and your INSERT sample data. If you only have them in phpMyAdmin, use Export → SQL to save a .sql file.
  • 2Create a new GitHub repository named after your app (example: lost-and-found-app). Add a README.md with the app name and the members' names.
  • 3Create this folder structure. You'll fill it in task by task.
your-app/
├── README.md
├── database/
│   ├── schema.sql        ← CREATE TABLE statements from your DB project
│   └── seed.sql          ← INSERT sample data
├── docs/
│   ├── 01-brief.md
│   ├── 02-crud-map.md
│   ├── 03-sitemap.png    ← plus user-flow.png
│   ├── 04-wireframes/    ← one image per screen
│   └── 05-style-guide.md ← or .png
└── prototype/
    ├── css/style.css
    ├── list.html
    └── form.html

Why prototype/ and not index.php? These pages are static mock-ups. In Week 15 you'll copy them into PHP files and replace the sample rows with real query results. Keeping them separate lets you compare "before" and "after".

TASK 1 · 5 POINTS

Write the project brief

About 30 mindocs/01-brief.md
Do this

Answer the questions below in 01-brief.md. Keep it to one page. Use short sentences, not paragraphs of filler.

# Project Brief: [App name]

## 1. The problem
Who has the problem, and what is hard for them today? (2–3 sentences)

## 2. Users and what they need to do
| User role | What they need to do in the app |
|-----------|---------------------------------|
| e.g. Student | Report a lost item, search found items |
| e.g. Admin   | Approve claims, manage categories   |

## 3. The database behind it
Database name, number of tables, and one sentence per table.

## 4. Must-have features (for the final project)
List 4–6. Each one should start with a verb: "Add...", "Search...", "Approve..."

## 5. Nice-to-have features (only if there's time)
List 1–3.

## 6. Similar apps I looked at
Name 1–2 real websites or apps and one idea you'll borrow from each.
Done when
  • At least two user roles are listed (a guest counts as a role)
  • Every table in your database is mentioned in section 3
  • Every must-have feature starts with a verb and uses at least one table
Hint · I only have one kind of user

Think about who manages the data versus who uses it. Most apps have at least a visitor (read-only) and an admin (can add, edit, delete). If your app really has only one role, explain why in section 2.

TASK 2 · 10 POINTS

Turn your tables into features: the CRUD map

About 45 mindocs/02-crud-map.md
Read

Every table in your database needs a way to be Created, Read, Updated, and Deleted, or a reason why not. A CRUD map shows which pages handle each table, and which user role may do each action. Here is an example for a campus lost-and-found app with four tables.

TableCRUDPagesWho
items✓✓✓✓items-list, item-view, item-formStudent: C, R, U own · Admin: all
categories✓✓✓✓categories (list + form in one page)Admin only
claims✓✓✓–claim-form, claims-listStudent: C · Admin: R, U status. Never deleted, kept as a record.
users✓✓✓–register, login, profileSelf: C, U · Admin: R. Deactivated, not deleted.
Read · from SQL column to form field

Your column types already tell you what each form field should be. Use this table when you plan forms.

Column in MySQLForm controlNote
id INT AUTO_INCREMENTnoneMySQL makes it. Don't put it on the "Add" form. On "Edit" it's a hidden field.
VARCHAR(n)<input type="text" maxlength="n">Use type="email" or "tel" when it fits.
TEXT<textarea>Long descriptions and notes.
INT / DECIMAL<input type="number">Add min, max, and step="0.01" for money.
DATE / DATETIMEtype="date" / "datetime-local"Skip it if MySQL fills it with DEFAULT CURRENT_TIMESTAMP.
ENUM('a','b')<select> or radio buttonsThe options are the ENUM values.
BOOLEAN / TINYINT(1)<input type="checkbox">Example: is_active.
Foreign key (category_id)<select> filled from the other tableShow the name, store the id: <option value="3">Gadgets</option>
NOT NULLrequiredMark it with * on the form.
Check yourself (not graded)
1. Your orders table has customer_id, a foreign key to customers. On the "Add order" form, this field should be…
2. Which columns should not appear as fields on an "Add" form?
3. Why might a table have no Delete in the CRUD map?
Do this
  1. Make a CRUD map table like the example for every table in your database.
  2. Below it, list the form fields for your two most important tables: column name → form control → required?
  3. Add a section "Schema changes". List any column or table you added, removed, or renamed while planning, and why. Write "None" if there were none.
  4. Update database/schema.sql if you changed anything.
Done when
  • Every table has a row, and every "–" has a reason
  • Each row names the pages and the user roles
  • Field lists for two tables follow the column-to-control table above
  • The "Schema changes" section exists
Hint · My table is a "link" table (many-to-many)

Tables like student_subjects or order_items rarely get their own page. They're usually managed inside another page: checkboxes on the student form, or an "Add item" row on the order page. Write that in the Pages column.

TASK 3 · 5 POINTS

Draw the sitemap and one user flow

About 30 mindocs/03-sitemap.png, docs/03-user-flow.png
Read

A sitemap shows every page and how pages link to each other. Take the page names from your CRUD map. A user flow follows one user doing one job, step by step, including what happens when something goes wrong.

Sitemap (example)                    User flow: Student reports a lost item
Home                                 Home → Login ─(wrong password)→ Login + error
├── Login / Register                          └─(ok)→ Dashboard
├── Items list ── Item view               → "Report item" → Item form
│                  └── Claim form              ─(missing field)→ Form + error message
├── Report item (Item form)                    └─(saved)→ Item view + "Saved" message
└── Admin
    ├── Claims list
    └── Categories
Do this
  1. Draw your sitemap. Every page in your CRUD map must appear. Mark pages only an admin can see.
  2. Pick your app's most important job and draw its user flow. Include at least one error path (wrong input, not logged in, nothing found).
  3. Export both as images. A clear photo of a paper drawing is fine.

  • Every page from the CRUD map is in the sitemap

TASK 4 · 10 POINTS

Sketch the wireframes

About 60 mindocs/04-wireframes/
Read

A wireframe is a simple black-and-white sketch of a screen: boxes for content, lines for text, no colors yet. It answers "what goes where?" before you spend time on CSS. Sketch these four screens at minimum:

1 · Home or dashboardNavigation, what the app is, the main buttons or a summary (e.g. "12 items found this week").
2 · List page (Read)A table or cards from your main table. Search or filter. Edit and Delete buttons on each row. An empty state.
3 · Form page (Create / Update)Fields from your Task 2 list, labels, required marks, Save and Cancel, an error message example.
4 · Detail pageOne record with its related data (e.g. an item with its category name and its claims).
Do this
  1. Sketch the four screens on paper, in draw.io, or in Figma. Desktop view is required; add a phone view for the list page.
  2. Label each box with the table and column it shows, for example items.title or categories.name.
  3. On the list page, also draw the empty state ("No items yet. Add the first one.").
  4. On the form page, show one error message next to a field.
  5. Save each screen as its own image in docs/04-wireframes/.
FigmaFree starter plan. Use frames sized 1440 wide (desktop) and 390 wide (phone).Tool

Keep it grey. Colors and fonts come in Task 5. If you start choosing colors now, you'll spend your time on looks instead of layout.

Done when
  • Four screens, plus a phone view of the list page
  • Boxes are labeled with table.column names
  • The empty state and an error message are shown
  • Every screen can be reached from the sitemap in Task 3
TASK 5 · 5 POINTS

Make a small style guide

About 30 mindocs/05-style-guide.md
Do this
  1. Choose 3–5 colors: primary, background, text, and one each for success and error. Write their hex codes.
  2. Check that your text color on your background passes WCAG AA (contrast ratio 4.5:1 or higher). Record the ratio.
  3. Choose 1–2 fonts (one for headings, one for body) and the base font size.
  4. Describe or show: the primary button, the secondary button, a text input, and an error message.
  5. Write these as CSS custom properties. You'll paste them into style.css in Task 6.
:root {
  --color-primary: #0b3d5c;   /* buttons, links, headings */
  --color-bg: #f5f7fa;        /* page background */
  --color-text: #12263a;      /* body text. Contrast on bg: 14.1:1 ✓ */
  --color-success: #23683f;
  --color-error: #a8352a;
  --font-heading: "Poppins", Arial, sans-serif;
  --font-body: "Inter", Arial, sans-serif;
  --radius: 8px;
}
WebAIM Contrast CheckerPaste two hex codes and read the ratio.Tool CoolorsGenerate and lock color palettes.Tool Google FontsFree web fonts with ready-made <link> tags.Tool
Done when
  • Colors are listed with hex codes, and the text/background ratio is 4.5:1 or higher
  • Fonts and base size are chosen
  • Buttons, inputs, and the error style are described
  • The CSS variables are written out
TASK 6 · 10 POINTS

Build two static pages

About 90 minprototype/
Do this

Turn wireframes 2 and 3 into real pages with HTML and CSS. No PHP or JavaScript is needed yet.

  1. list.html: your list page. Type in at least 5 rows copied from your seed.sql so it looks real. Include the navigation, a search box, and Edit/Delete buttons (they don't need to work yet).
  2. form.html: your Add form for the same table. Use the controls from your Task 2 field list, with <label> for every field and required where the column is NOT NULL.
  3. Both pages use one shared css/style.css that starts with your style-guide variables.
  4. Make the list page work on a phone (390px wide): no sideways scrolling of the whole page. Use what you learned about responsive layout in Week 8.
  5. Give each input a name that matches the column name exactly. In Week 15, PHP will read $_POST['title'], so the names must match.
<form action="#" method="post" class="form">
  <!-- name="..." matches the column in the items table -->
  <label for="title">Item name *</label>
  <input id="title" name="title" type="text" maxlength="100" required>

  <label for="category_id">Category *</label>
  <select id="category_id" name="category_id" required>
    <option value="">Choose one</option>
    <option value="1">Gadgets</option>     <!-- rows from categories -->
    <option value="2">IDs and cards</option>
  </select>

  <label for="date_found">Date found</label>
  <input id="date_found" name="date_found" type="date">

  <p class="error">Please choose a category.</p>   <!-- sample error -->
  <button type="submit">Save</button>
  <a href="list.html" class="btn-secondary">Cancel</a>
</form>
Hint · My table has many columns and looks cramped on a phone

Wrap the table in <div class="table-wrap"> with overflow-x: auto, so only the table scrolls. Or, under a media query, show each row as a card. Show the 3–4 most useful columns in the list; the rest belong on the detail page.

Hint · Should I use Bootstrap?

You may, but you must still apply your own style-guide colors and fonts, and you must explain any class you use. Plain CSS with your variables is perfectly fine and easier to explain.

Done when
  • Both pages open from the prototype/ folder with Live Server, and the links between them work
  • The list shows at least 5 real rows from your seed data
  • Every field has a label, and every name matches a column
  • One shared stylesheet uses your style-guide variables
  • The list page has no sideways page scroll at 390px (test with DevTools → device toolbar)
  • The pages match your wireframes. If you changed something, say what in your reflection.
